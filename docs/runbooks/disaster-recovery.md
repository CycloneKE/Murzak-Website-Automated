# Disaster recovery: rebuilding after the server is lost

**For:** whoever has to bring Murzak back after the VPS is destroyed, corrupted or locked out.
**Status:** first draft, written from what the repositories describe. **It has never been rehearsed.**
Every line marked **CONFIRM** is something the repositories do not prove and a person with server
access must check. Until those are checked and one restore has been practised, treat the recovery
times in this document as hopes, not commitments.

## Why this exists

Everything runs on one server (`187.124.217.78`, Hostinger KVM 2, 8 GB RAM):

- the public website and customer portal (a Coolify application),
- the website's Frappe site, which is the record of every account, invoice, order and build job,
- every customer's POS and ERP site (one Frappe site and one MariaDB database each, on the bench in
  `/home/murzakerp/frappe-bench`),
- the shared POS site `api.pos.murzaktech.tech`,
- Coolify itself and everything it hosts (customer websites, databases, apps, MinIO storage),
- Stalwart mail,
- nginx and every TLS certificate.

If that server is lost, all of it is lost at once. What survives is exactly what was copied
somewhere else beforehand. This document lists what must be copied, and the order to rebuild in.

## 1. What must exist off the server

Check this table every quarter. A row without a tested off-server copy is data that will not come
back.

| What | Where it lives on the server | How it is copied off | State |
|---|---|---|---|
| Every Frappe site: database, uploaded files, `site_config_backup.json` (holds that site's encryption key) | `~/frappe-bench/sites/<site>/` | `backup_sites.sh` in the Murzak-PoS-Backend repository, with `BACKUP_REMOTE` set (its `docs/BACKUPS.md`) | Script covers every site automatically. **CONFIRM** `BACKUP_REMOTE` is set in the cron line; without it nothing leaves the server |
| Mail (Stalwart data directory) | `STALWART_DATA_DIR` | `murzak-stalwart-backup` timer with an rclone `BACKUP_DEST` | **CONFIRM** `BACKUP_DEST` is a remote, not a local folder |
| Coolify's own database and settings | Coolify's Postgres container, `/data/coolify` | Coolify: Settings, Backup, with an S3 destination | **CONFIRM** it is switched on and points off the server |
| Coolify's `APP_KEY` | `/data/coolify/source/.env` | By hand, into the password manager | **CONFIRM**. Without this key a restored Coolify database cannot decrypt its own secrets |
| Customer databases and volumes hosted through Coolify | Docker volumes | Per-resource scheduled backups in Coolify, or `BACKUP_CONFIG_CMD` (see `backend/services/provisioning/backups.js`) | **Not set up as far as the repository shows.** Jobs record `backup_status: skipped` when no provider is configured. Check the Provisioning panel |
| MinIO object storage (customer files) | Docker volume | Bucket replication or `rclone sync` to another provider | **CONFIRM**, nothing in the repository does this |
| Server secrets | `/etc/murzak/*.env`, `/root/.murzak-db-root-password`, `/root/.config/rclone/` | By hand, into the password manager | **CONFIRM** |
| The website's environment variables | Coolify, the application's environment panel | By hand, into the password manager. Names are listed in `backend/.env.example` | **CONFIRM** |
| nginx configuration and helper scripts | `/etc/nginx`, `/usr/local/bin/murzak-*`, `/etc/systemd/system/murzak-*` | Already in this repository under `deploy/vps/` | Done, provided the server matches the repository. Per-app vhosts are regenerated by `murzak-app-sync` |
| TLS certificates | `/etc/letsencrypt` | Not needed: they can be issued again (section 3, step 5) | Nothing to do |
| Application code | n/a | GitHub | Done |

Three things are worth more than the rest, because nothing can recreate them: the **Frappe site
backups**, the **encryption keys** (each site's `encryption_key`, and Coolify's `APP_KEY`), and the
**password manager entries**. A database restored without its encryption key comes back with every
saved password (payment gateway keys, email accounts) unreadable.

## 2. Accounts you will need, and must be able to reach without the server

Keep these logins, with their two-factor recovery codes, somewhere that does not depend on Murzak
email (the mail server is on the lost box):

- **Hostinger**: the VPS, DNS for `murzaktech.tech`, and the API token used for DNS-01 certificates.
- **GitHub**: the `CycloneKE` and `MurzakTech` organisations (code, deploy workflows, container images).
- **The off-server backup storage** and the rclone crypt password.
- **Safaricom Daraja** (M-Pesa) and **PayPal**: to update callback and webhook addresses if the IP changes.
- **Firebase** (Google sign-in) and the **SMTP** provider.

## 3. Rebuild order

Each step depends on the one before it. Do not skip ahead.

1. **Decide: restore a snapshot, or rebuild.** If Hostinger has a recent snapshot of the VPS,
   restoring it is far faster than everything below. **CONFIRM** snapshots or Hostinger's weekly
   backups are switched on. Then jump to step 9 and restore only what changed since the snapshot.
2. **New server.** Same size or larger, Ubuntu, with a 2 GB swapfile (`deploy/vps/README.md`,
   "Prerequisites on the box"). Note its IP address.
3. **Base software.** Docker, nginx, certbot, MariaDB, rclone, jq, then Coolify.
4. **Server secrets back in place.** `/etc/murzak/*.env`, `/root/.murzak-db-root-password`
   (set MariaDB's root password to match), `/root/.config/rclone/rclone.conf`.
5. **DNS and certificates.** If the IP changed, update these A records at Hostinger: the apex,
   `www`, `website`, `*.apps`, `*.erp`, `*.pos`, `pos`, `api.pos`, `erp` and the mail records.
   Issue the certificates again: `murzaktech.tech` (HTTP-01) and the wildcards `apps-wildcard`,
   `erp-wildcard`, `pos-wildcard` (DNS-01 through `deploy/vps/bin/certbot-hostinger-dns`).
   Let's Encrypt limits how many certificates a domain can be issued per week, so issue each once and
   do not retry in a loop.
6. **nginx and helpers.** Install everything in the table in `deploy/vps/README.md`, enable the
   sites, `nginx -t`, reload.
7. **The bench.** Create the `murzakerp` user, install Frappe bench with the same Frappe and ERPNext
   versions (`docs/frappe-bench-apps.md`), and get the apps, including `murzak_pos`.
8. **Restore the website's Frappe site first.** It is the record of who has paid for what; nothing
   else can be trusted until it is back. **CONFIRM** which site this is (the value of
   `FRAPPE_BASE_URL` in the website's environment). `bench new-site`, `bench restore`, then copy the
   `encryption_key` from its `site_config_backup.json` into the new `site_config.json`.
9. **Restore every customer site**, the same way, from the off-server backups. One folder per site
   on the remote. Restore `api.pos.murzaktech.tech` and paying customers' shops first.
10. **Coolify.** Restore its database backup, put the saved `APP_KEY` back in
    `/data/coolify/source/.env`, and confirm the server and resources appear.
11. **The website.** Redeploy the application in Coolify from GitHub with its environment variables
    restored, and attach its domains (`deploy/vps/README.md`, "Bringing the main site up").
12. **Mail.** Restore the Stalwart data directory from its backup (`docs/runbooks/email-hosting.md`).
13. **Timers.** Enable `murzak-bench-runner.timer`, `murzak-app-sync.timer`,
    `murzak-stalwart-backup.timer`, and put the nightly `backup_sites.sh` cron line back.
14. **Payment addresses.** If the IP or host changed, check `MPESA_CALLBACK_URL` and the PayPal
    webhook address still reach the server.

## 4. Proving it is back

- `https://murzaktech.tech/api/health/deep` answers `"ok":true`.
- Sign in to the portal as a test customer; invoices and services show.
- Open one customer's shop at `<shop>.pos.murzaktech.tech` and sign in.
- Portal, admin, Provisioning: readiness is green and no job is stuck in `running`.
- Make one real KES 1 M-Pesa payment on a test invoice and see it turn Paid.
- Send and receive one email on a hosted mailbox.
- The next morning, the backup log shows every site `OK ... (copied off the server)`.

## 5. Telling customers

Payments made in the hours before the loss may be newer than the last backup. After the restore:

- Compare the M-Pesa and PayPal statements for the period since the last backup against Portal
  Invoices, and mark the missing ones Paid by hand. The paid-order reconciler then starts their
  builds.
- Shops lose whatever was sold after their last nightly backup. Tell each shop owner the exact time
  their data was restored to, so they can re-enter sales from paper or M-Pesa messages.

## 6. Known weak points, to decide on

- **One server.** Every product shares one failure. The cheapest meaningful improvement is moving
  the website and its Frappe site to a second small server, so customers can still sign in, pay and
  be told what is happening while the tenant server is rebuilt.
- **Capacity.** The server had about 3,500 MB free when measured on 2026-09-05, and the catalogue
  treats 3,000 MB of that as sellable. With the default limit of 85% the gate commits up to
  2,550 MB, leaving under 1 GB spare. Setting `PROVISIONING_RAM_THRESHOLD_PCT=70` in the website's
  environment leaves about 1.4 GB spare (`backend/.env.example` explains the trade-off). The
  measurement is two months old: run `free -m` on the server and re-check it.
- **Backups are nightly.** Up to a day of each shop's sales can be lost. Shortening that needs
  MariaDB binary logs shipped off the server, which is not set up.
- **This has not been rehearsed.** Restore one customer site onto a scratch server, time it, and
  correct this document with what actually happened.
