# VPS-side files for app subdomain routing

Source of truth for the nginx config and helper scripts that make
`*.apps.murzaktech.tech` reachable. These are **deployed to the VPS**, not used
by the Node app — kept here so they are version-controlled rather than living
only on `srv1657915`.

See [`docs/app-subdomain-routing.md`](../../docs/app-subdomain-routing.md) for
the design and the reasoning behind it.

## Prerequisites on the box

- `/var/www/certbot/.well-known/acme-challenge/` exists (ACME webroot).
- **A 2 GB swapfile at `/swapfile`, with `vm.swappiness=10`.** Added
  2026-09-05; the box ran with zero swap until then. It is a cushion, not
  capacity: with ~3.5 GB genuinely free and a capacity gate willing to commit
  5.4 GB (see below), an overshoot without swap is not slowness — it is the
  OOM killer picking a container to destroy, possibly a paying customer's.
  Swappiness is lowered from the default 60 so the kernel reclaims cache
  before it pages, keeping swap for real pressure rather than routine use.

  ```bash
  sudo fallocate -l 2G /swapfile && sudo chmod 600 /swapfile
  sudo mkswap /swapfile && sudo swapon /swapfile
  echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
  echo 'vm.swappiness=10' | sudo tee /etc/sysctl.d/99-murzak-swappiness.conf
  sudo systemctl daemon-reload   # else systemd keeps the stale fstab view
  ```

  Verify persistence without rebooting — `swapon -a` reads fstab, so this
  proves the reboot path rather than assuming it:

  ```bash
  sudo swapoff /swapfile && sudo swapon -a && sudo swapon --show
  ```

  **This does not fix the capacity accounting.** `sellableRamMb: 6400` in the
  catalog reserves ~1.8 GB for overhead, but the box actually carries ~4.3 GB
  of non-sellable load (OSRM 887 MB, tileserver 453 MB, the Coolify stack,
  minio, other tenants). Measured 2026-09-05: 7,941 MB total, ~3,500 MB free.
  That constant still needs a decision.
- `server_names_hash_bucket_size 128;` is set in `nginx.conf` — the default 64
  is too small for the ~64-character hostnames the provisioner generates.
- A wildcard DNS record `*.apps.murzaktech.tech A -> 187.124.217.78`.
- For the main site, an apex record `murzaktech.tech A -> 187.124.217.78` and
  `www.murzaktech.tech` following it. See *Bringing the main site up* below —
  as of 2026-09-03 the apex still pointed at Hostinger's parking IP
  (`2.57.91.91`), which is why the public site was unreachable while the apps
  wildcard worked fine.
- A self-signed fallback certificate for the `:443` catch-all:

  ```bash
  sudo mkdir -p /etc/ssl/murzak
  sudo openssl req -x509 -nodes -newkey rsa:2048 -days 3650 \
    -keyout /etc/ssl/murzak/apps-fallback.key \
    -out /etc/ssl/murzak/apps-fallback.crt \
    -subj "/CN=unpublished.apps.murzaktech.tech" \
    -addext "subjectAltName=DNS:*.apps.murzaktech.tech,DNS:unpublished.apps.murzaktech.tech"
  sudo chmod 600 /etc/ssl/murzak/apps-fallback.key
  ```

## Bringing the main site up

`nginx/murzaktech.tech` is the apex vhost. Four things have to line up, in
this order — each step's failure mode is different, so verify as you go rather
than doing all four and debugging the result.

1. **DNS.** Point the apex at the box in Hostinger's DNS panel:

   | Record | From | To |
   |---|---|---|
   | `murzaktech.tech` A | `2.57.91.91` (parking) | `187.124.217.78` |
   | `www` | follows the apex | unchanged |

   Verify: `nslookup murzaktech.tech` returns `187.124.217.78`. Until it does,
   step 2's HTTP-01 challenge cannot succeed.

2. **Certificate.** With DNS live, HTTP-01 works because the `:80` block above
   serves `/var/www/certbot`:

   ```bash
   sudo certbot certonly --webroot -w /var/www/certbot \
     --cert-name murzaktech.tech \
     -d murzaktech.tech -d www.murzaktech.tech
   ```

   To issue *before* flipping DNS, use `bin/certbot-hostinger-dns` (DNS-01)
   instead. Note the `:443` block references
   `/etc/letsencrypt/live/murzaktech.tech/` — `nginx -t` fails until the cert
   exists, so issue it before enabling the site.

3. **Enable the vhost.**

   ```bash
   sudo ln -s /etc/nginx/sites-available/murzaktech.tech \
              /etc/nginx/sites-enabled/murzaktech.tech
   sudo nginx -t && sudo systemctl reload nginx
   ```

4. **Attach the domain in Coolify.** nginx forwards to Traefik, and Traefik
   routes on the Host header — it has no route for `murzaktech.tech` until the
   domain is attached to the application in Coolify. A **503 with a valid
   certificate** means exactly this step is missing. Attach via
   `urls: [{ name, url }]` (Coolify 4.1.2 rejects a `domains` key with a 422),
   then confirm the app restarts — Coolify does not always restart on domain
   attach, and the route does not take effect until it does.

Also set, in the Coolify environment panel (then redeploy — env changes do not
reach a running container):

```
APP_BASE_URL=https://murzaktech.tech
FREE_SUBDOMAIN_ROOT_DOMAIN=murzaktech.tech
APP_DOMAIN_BASE=apps.murzaktech.tech
```

## Provisioning bench tenants

`bin/murzak-bench-provision` is what `BENCH_PROVISION_CMD` points at. Without
it the bench lane is enabled-but-unconfigured, and **every premium sale — ERP,
POS, CRM, the KES 6,000–12,000/mo tier — fails with "Bench lane not
configured"**. The four sites on the box today were all created by hand.

It runs on the VPS. The app runs in a Coolify container and cannot reach
`/home/murzakerp/frappe-bench`, so `BENCH_PROVISION_CMD` is **never set in the
container** — that is deliberate, not an oversight, see "How the container
gap is actually closed" below.

### Before it can run

Three prerequisites, each of which the script checks and refuses on rather
than producing a broken tenant:

1. **`BENCH_DB_ROOT_PASSWORD`** — ✅ **recovered 2026-09-12.** Root was on
   password-only auth with the password unrecorded. Reset via `--init-file`
   (never `--skip-grant-tables`, which disables auth while customer sites are
   live) to **multi-auth**: `unix_socket` so `sudo mysql` always works and this
   cannot recur, plus `mysql_native_password` for bench over TCP. The password
   is at `/root/.murzak-db-root-password` (0600). **Lesson that took the DB
   down on the first attempt:** mysqld runs as `mysql` and cannot read files in
   `/root` (0700) — an unreadable init file aborts startup and every Frappe
   site goes with it. Put it somewhere `mysql` can read and check before
   restarting.
2. **Wildcard DNS, certificate and vhost** — ✅ **live 2026-09-13.**
   `*.erp.murzaktech.tech A -> 187.124.217.78`, certificate `erp-wildcard`
   issued by DNS-01 through `certbot-hostinger-dns` (auto-renews like
   `apps-wildcard`), and `nginx/erp-tenants-wildcard` enabled. Verified an
   unprovisioned tenant gets a valid certificate and Frappe's "Not Found",
   while every existing site kept its own certificate — exact server_name
   beats a wildcard, so nothing was displaced. The vhost is deliberately **not**
   in `conf.d/frappe-bench.conf`: that file is regenerated by
   `bench setup nginx` and anything added there vanishes.
3. **Every app in the product's `benchApps` already on the bench.** Adding one
   mid-provision is not safe: `bench get-app` pip-installs into the shared
   virtualenv and the app is not importable until the workers restart, which
   briefly 500s *every* tenant (observed 2026-09-05 installing `hrms`). The
   script refuses so a human can schedule it.

### Status: host script proven end-to-end, automated 2026-09-14

`murzak-bench-provision` is **installed** at `/usr/local/bin/` and **passed an
end-to-end test on 2026-09-13**: it created a real tenant, installed
`erpnext + hrms + csf_ke`, and the site served Frappe's login page at
`https://<tenant>.erp.murzaktech.tech` over the wildcard certificate, with the
API answering. Then it was dropped. Three runs, each proving something:

| Run | Result | Proved |
|---|---|---|
| 1 | **exit 1** at `install-app hrms`, 133s | a real bug (below) — and that failure emits zero stdout and a retryable code, as the lane requires |
| 2 | exit 0, 25s | idempotency: adopted the site, skipped installed apps, `admin` correctly empty |
| 3 | exit 0 | the hrms repair gate does **not** fire on a healthy site |

The bug run 1 caught — **every `biz-erp-light` and `starter-hrpay` sale
would have failed**: `hrms`'s `after_install` refuses unless
`user_type_doctype_limit` is set in site config, and a fresh site never has
it. Worse, Frappe marks an app installed *before* its post-install hook runs,
so the abort left `hrms` listed as installed with four setup steps never
executed — and a naive retry skips it forever. The script now sets the config
first (4b) and repairs an aborted setup (6b). **`erp.murzaktech.tech` has this
same half-installed `hrms`** and has not been repaired.

### How the container gap is actually closed: `murzak-bench-runner`

An earlier design (`murzak-bench-provision-remote`, removed) put an SSH key
for a sudo-capable host user inside the internet-facing app container so IT
could reach across and run the script. Rejected before it was ever installed:
a remote-code-execution bug in the app would become full host compromise —
MariaDB root, the zone-wide DNS token, every tenant's data.

`murzak-bench-runner` (`bin/murzak-bench-runner`) inverts the direction
instead. The container **never gets host access, ever**. Here is why that is
possible without racing the container's own runner:

`backend/services/provisioning/runner.js` polls for `status=queued` jobs and,
finding `BENCH_PROVISION_CMD` unset in the container (which it now always
will be — this is deliberate, not a gap to fill), escalates every bench job to
`status=needs_human` within its normal poll interval and files a "delayed,
engineers notified" ticket. That happens fast and unconditionally. So
`murzak-bench-runner` does not compete for `queued` at all — by the time any
reasonable host timer looks, the job is already sitting at `needs_human`,
untouched by anything else. The host script polls **that** state instead,
which means:

- No claim race with the live container runner — it already moved on.
- The host script needs its own lock only against **itself** (two overlapping
  runs of the timer), which it does the same way `runner.js`'s `claimJob` does:
  write `status=running` + a runner id, re-read to confirm the write stuck.
- If the host script is killed mid-run (reboot, lost SSH, OOM), the *next* run
  reclaims anything left `running` under its own runner-id prefix back to
  `needs_human` before fetching new work, so a crash never strands a job.

It talks to Frappe directly over HTTPS with a scoped API key (bash + curl +
jq — this box has no Node runtime outside the bench's own venv, and shipping
one just for this felt like the wrong trade against a 260-line script). Exit
codes from `murzak-bench-provision` are honoured exactly as the Node lane
would: `0` → job goes `active` and the Web Account row flips `Setting up` →
`Active`; `2` → permanent, `attempts` is pinned at the max so the job is never
refetched (still visible to a human, who can reset `attempts` via the existing
retry button to try again after fixing the cause); `1` → `attempts+1`, retried
on a later run while still under the cap.

**Installing it:**

```bash
sudo install -m 0755 bin/murzak-bench-runner /usr/local/bin/
sudo install -d -m 0700 /etc/murzak
```

Two files it needs, both root-only and **never committed**:

```bash
# /etc/murzak/frappe-api.env — same credential the app container already
# holds; the host is at least as trusted (it already has the DB root
# password), so this reuses rather than mints a second secret.
FRAPPE_BASE_URL=https://erp.murzaktech.tech/
FRAPPE_API_KEY=...
FRAPPE_API_SECRET=...
```

```bash
# /etc/murzak/bench-catalog-snapshot.json — a copy of
# backend/data/serviceCatalogSnapshot.json. Reference data only, no secrets.
# Update it by hand after any catalogue change that touches benchApps, same
# manual-scp discipline as every other file in this directory.
sudo cp backend/data/serviceCatalogSnapshot.json /etc/murzak/bench-catalog-snapshot.json
```

Then the timer:

```bash
sudo install -m 0644 systemd/murzak-bench-runner.service /etc/systemd/system/
sudo install -m 0644 systemd/murzak-bench-runner.timer /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now murzak-bench-runner.timer
```

Provisioning a tenant by hand still works and is unaffected:

```bash
sudo JOB_WEB_ACCOUNT=<account> JOB_SERVICE_ID=<service> \
     JOB_BENCH_APPS=<apps from the catalog> \
     BENCH_DB_ROOT_PASSWORD="$(sudo cat /root/.murzak-db-root-password)" \
     /usr/local/bin/murzak-bench-provision
```

### Contract

The lane execs the script with the job in the environment and **parses the last
line of stdout as JSON**, so the script writes only its result there and sends
every diagnostic to stderr. Exit 2 means "do not retry, escalate"; exit 1 is
retryable; the runner's timeout is `BENCH_PROVISION_TIMEOUT_MS` (default 10
minutes).

It is idempotent by design, because the runner retries: an existing site is
adopted rather than recreated, and apps already installed are skipped. The
`admin` field is empty for an adopted site — the existing password is unknown
and inventing one would be worse than returning nothing.

## Shop email (outgoing mail for customer POS shops)

A new shop starts with no Email Account, so its own "Email me a code" password
reset fails with "We could not send the email just now". `bin/murzak-shop-mail`
adds one, and `murzak-bench-provision` calls it for every new POS shop (a
failure there never blocks the build; it only logs a warning).

**Use a dedicated key from a transactional mail provider (Brevo, Mailgun, Amazon
SES), never the Gmail account that api.pos uses.** Every shop owner is System
Manager on their own site, and a System Manager can read a stored Password
field through Frappe's own API, so whatever credential goes into a shop is
readable by that customer. A dedicated, quota-limited key limits the damage to
one replaceable credential.

One-time setup on the VPS:

1. In the provider, add and verify `murzaktech.tech` as a sending domain (it
   gives you SPF and DKIM DNS records; add a DMARC record too), then create an
   SMTP key.
2. Install the script: `sudo install -m 0755 bin/murzak-shop-mail /usr/local/bin/`
3. Create the config. The password prompt does not echo and never lands in shell
   history, and `%q` quotes it safely:

   ```bash
   sudo bash -c '
   umask 077
   read -r -p "SMTP host: " H
   read -r -p "SMTP login: " U
   read -rs -p "SMTP password/key: " P; echo
   {
     printf "SHOP_SMTP_HOST=%q\n" "$H"
     printf "SHOP_SMTP_PORT=587\n"
     printf "SHOP_SMTP_SECURITY=starttls\n"
     printf "SHOP_SMTP_USER=%q\n" "$U"
     printf "SHOP_SMTP_PASSWORD=%q\n" "$P"
     printf "SHOP_MAIL_FROM=no-reply@murzaktech.tech\n"
     printf "SHOP_MAIL_NAME=%q\n" "Murzak POS"
   } > /etc/murzak/shop-mail.env
   chmod 600 /etc/murzak/shop-mail.env'
   ```

4. Apply it to a shop that already exists, then try "Email me a code" on it:

   ```bash
   sudo murzak-shop-mail <slug>.erp.murzaktech.tech
   ```

Saving the account makes Frappe open a real SMTP connection, so a wrong host,
login or key fails right there with the provider's message.

To rotate the key, edit `/etc/murzak/shop-mail.env` and re-run
`murzak-shop-mail` for every shop (it accepts several site names). It updates
the existing account in place.

## Shop setup (business type, kitchen and bar)

While a new POS shop builds, the owner answers a few questions on the website
(`backend/services/apps/shopSetup.js` defines the choices). The answers are saved
on their Checkout Order. `bin/murzak-shop-setup` applies them once the shop
exists, through `murzak_pos`'s own `save_business_kind` and
`save_kitchen_settings`. `murzak-bench-runner` calls it on every run, so there is
nothing extra to schedule.

1. Install the script: `sudo install -m 0755 bin/murzak-shop-setup /usr/local/bin/`
2. Install the updated runner: `sudo install -m 0755 bin/murzak-bench-runner /usr/local/bin/`
3. Apply to one shop by hand (the plan comes from the order, so this is only for
   testing): `echo '{"version":1,"kind":"retail","kitchen":null,"itemGroups":[]}' | sudo murzak-shop-setup apply <slug>.erp.murzaktech.tech`
4. Watch it work: `journalctl -u murzak-bench-runner.service --since "10 min ago" --no-pager | grep -i "shop setup"`

It only adds. A business type or kitchen settings the owner already saved are
kept, and the owner is told so. A failure is retried 3 times, then marked
`failed`; the shop itself is never affected.

### The shop's Company (made automatically)

A shop bought on the website is built with an owner login but no **Company**,
the business record the POS set-up wizard, Business settings and the till all
hang off. Public sign-up is the only other thing that makes one, and it is closed
on shop addresses, so without this the owner signs in to "We could not load your
shop details" and cannot continue.

`murzak-shop-setup company` (run first by every `sweep`, and straight after a POS
build by `murzak-bench-runner`) makes it the way sign-up does, as the owner: the
shop name the buyer typed at checkout, Kenya and KES, the owner's contact, default
accounts, a POS profile, and the owner's default company and permission. A shop
that already has a Company is left alone. The result is kept on the order
(`shopCompany`), a failure is retried 3 times, and the other shop-setup steps wait
for it.

- One shop by hand (also how to repair a shop built before this existed):
  `sudo murzak-shop-setup company <slug>.erp.murzaktech.tech "<Shop name>" <owner email>`
- Run the check for every finished POS shop now: `sudo murzak-shop-setup company`
- Test without a server: `bash deploy/vps/test/shop-company.test.sh`
- Install: `sudo install -m 0755 bin/murzak-shop-setup /usr/local/bin/` and
  `sudo install -m 0755 bin/murzak-bench-runner /usr/local/bin/`

### Shop progress (portal checklist)

`murzak-shop-setup` also reads a few facts from each young shop, read-only, for
the portal's "Getting your shop going" checklist: signed in, products added,
till opened, first sale, staff added. The runner's `sweep` runs it, so nothing
extra is scheduled. The facts are saved on the owner's order, never in the shop.

- Look at one shop by hand (read-only): `sudo murzak-shop-setup signals <slug>.erp.murzaktech.tech`
- Run the progress pass now: `sudo murzak-shop-setup progress`
- "Signed in" uses the user's `last_active` (10+ minutes after the account was
  created), not `last_login`, which murzak_pos sign-ins do not set.
- Each shop is read every 10 minutes for its first 3 days, hourly after that, and
  not at all once signed in, products, till and first sale are all done.

## Switching a shop off when the subscription lapses

Until now a lapsed subscription only marked the customer's Web Account
"Suspended" on the website; the shop kept trading. `bin/murzak-shop-lifecycle`
makes the shop follow the account. `murzak-bench-runner` calls it on every run
(about every 90 seconds), so nothing extra is scheduled.

For each customer shop it reads the owner's Web Account. The shop is switched
**off** when the account is Suspended or Cancelled, or when a POS service row is
Suspended; it is switched back **on** when the account is paid up again.
"Off" is `maintenance_mode` in that shop's `site_config.json`: every request gets
Frappe's "Session Stopped" (HTTP 503), and nothing is deleted. It only ever
switches back on a shop it switched off itself, so a shop you put into
maintenance by hand stays that way. If the account cannot be read, the shop is
left as it is. The company's own sites (no owner stamp) are never touched.

Suspension itself is still the website's choice: it happens only when
`RENEWAL_SUSPEND_ENABLED=true` on the backend (see `renewalService.js`). With
that unset, no account is ever marked Suspended and this script changes nothing.

1. Install: `sudo install -m 0755 bin/murzak-shop-lifecycle /usr/local/bin/`
2. Install the updated runner: `sudo install -m 0755 bin/murzak-bench-runner /usr/local/bin/`
3. Rehearse first, changing nothing: `sudo murzak-shop-lifecycle sweep --dry-run`
   (it prints which shops it would switch off or on).
4. By hand for one shop: `sudo murzak-shop-lifecycle off <slug>.erp.murzaktech.tech`
   and `sudo murzak-shop-lifecycle on <slug>.erp.murzaktech.tech`.
5. Watch it work: `journalctl -u murzak-bench-runner.service --since "10 min ago" --no-pager | grep -i "lifecycle"`

Test the script without touching a server: `bash deploy/vps/test/shop-lifecycle.test.sh`.
